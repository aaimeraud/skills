# CLAUDE.md

Agent skills organised by topic and use case, each use case installable as a Claude Code plugin. The repository is meant to grow, so keep every addition in the same shape.

## Layout

```text
.claude-plugin/marketplace.json   # One entry per plugin (per use case)
release-please-config.json        # Release packages: one per plugin
.release-please-manifest.json     # Current version of each release package
.github/workflows/release-please.yml  # Opens the release PR on push to main
docs/workflows/                   # Example workflows, one file per use case
skills/<topic>/                   # Topic, for example education
  README.md                       # Index of the topic's plugins
  <use-case>/                     # Plugin, for example homework
    .claude-plugin/plugin.json    # Lists the plugin's skills and its version
    CHANGELOG.md                  # Generated by release-please
    <skill>/SKILL.md              # One skill, invoked as /<use-case>:<skill>
```

- A skill's folder name is its command name, so `name` in its frontmatter must match the folder.
- Each skill must be self-contained. The skills.sh installer copies only the skill's own folder, so a `SKILL.md` must not link to files outside it. Repeat the short rules it needs in its own file.
- Keep each `SKILL.md` short. Put long reference material in the one skill that needs it.

## Adding a skill

1. Create `skills/<topic>/<use-case>/<skill>/SKILL.md` with `name` and `description` in the frontmatter.
2. Add `./<skill>` to the plugin's `.claude-plugin/plugin.json`.
3. List the skill in the topic's `README.md` and in the table in the root `README.md`.
4. Run `claude plugin validate . --strict` and `claude plugin validate skills/<topic>/<use-case> --strict`.

## Adding a plugin (use case)

Do the same as for a skill, plus:

- Add one entry to `.claude-plugin/marketplace.json` (`name`, `source` as `./skills/<topic>/<use-case>`, `description`, `category`, `keywords`).
- Add the plugin to `release-please-config.json` (as a package, with a `package-name` equal to the plugin name, so that each plugin gets its own tag such as `linear-v1.0.0`) and to `.release-please-manifest.json` with the starting version `0.0.0`.
- Set the plugin's `version` in `plugin.json` to `0.0.0` as well.
- List the plugin in the topic's `README.md`.

## Example workflows

`docs/workflows/` shows how the skills fit together, one file per use case, listed in its `README.md`. Each file has: when to use it, the commands (with a Mermaid diagram), a short sample exchange, and what the agent does not do. Examples use a made-up project. When a skill's commands or behaviour change, update the workflows that show it.

## Changelog

Changelogs and versions are generated by release-please, not written by hand. It reads the Conventional Commit history on `main`, opens a release PR that updates each plugin's `CHANGELOG.md` (inside the plugin folder) and the `version` in its `plugin.json`, and creates the tag and GitHub Release when that PR is merged.

- Do not edit a plugin's `CHANGELOG.md` or bump its version by hand.
- Pull requests are squash-merged, so the PR title becomes the commit that release-please reads. It must be a Conventional Commit (`feat(education): ...`, `fix(education): ...`, and so on). A `feat` normally bumps the minor version, a `fix` the patch, and `!` or a `BREAKING CHANGE` footer a major version. While a plugin is below 1.0, release-please's exact bump can differ, so check the version in the release PR before merging it.
- Config lives in `release-please-config.json` and `.release-please-manifest.json`. Each plugin is a package there, so add a plugin to both files when you create one.

## Education skills (`homework`)

- The skills guide the student and never give the answer, the final code, or the correct result. Each skill repeats the ground rules it needs.
- The `.homework/` folder is the student's private working folder. Setup adds it to `.gitignore`. Never commit student material, briefs or answers to this repository.
- Commands are invoked as `/homework:<skill>`, so a skill called `homework` would be a different command.
- `homework` is for school work in any subject, graded against the brief. Personal coding projects belong in `mentor`.

## Mentor skills (`mentor`)

- For personal coding projects: no grade, the goal is to understand concepts. The skills never write the code the current task asks for, and examples are always on a different problem. Each skill repeats this rule.
- The `.mentor/` folder is the learner's private working folder. Setup adds it to `.gitignore`.
- The task can come from a Linear project. `sync` copies it into `.mentor/linear/`; the skills read Linear only, and `journal` is the one skill that writes to Linear, after the learner approves the entry.
- Commands are invoked as `/mentor:<skill>`.

## Project management skills (`linear`)

- The skills write content that any future teammate reads, so Linear text stays neutral and impersonal: no "you", "we" or "I", roles instead of people, and issue identifiers instead of task numbers.
- Examples in a skill must be generic. Never reference one person's project, handle or team key, and mark them with "for example".
- Nothing is created in Linear before the user approves the outline. Every field follows the language of the conversation, headings included, so templates written in English must be translated.
- Commands are invoked as `/linear:<skill>`.

## Documentation links

Only link official documentation or well-known free resources, and check each link before adding it. Each skill keeps its own short list of links. The full catalogue is in `skills/education/homework/topic-resources/SKILL.md`.

## Git

- Use git, or the version-control tool you prefer, for commits and branches. Do not commit to `main`. Use `type/short-description` branch names.
- Commit titles use Conventional Commits with the topic as scope where it applies, for example `feat(education): ...`.
- Open pull requests as drafts, following `.github/PULL_REQUEST_TEMPLATE.md`, unless the user asks for ready for review. Never merge a pull request.
- Prose, skill text, commit messages and pull requests are in English.
- Do not commit secrets, `.env` files, or the `.homework/` and `.mentor/` folders.
